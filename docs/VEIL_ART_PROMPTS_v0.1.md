## 0. 口径说明（「三重帷幕」的两种读法，本稿都覆盖）

| 读法 | 含义 | 本稿对应 |
|---|---|---|
| **甲（主读法）** | 三道门 = 三条飞升路径（硅基承续 / 虚境升华 / 渊血演化）都要生图 | 素材 B / C / D，三张门体 |
| 乙 | `veil.count` 第 1 / 2 / 3 重帷幕各有自己的画面 | 素材 E / F，只换「裂隙宽度 + 织物厚度」，**绝不重出门体** |

⚠️ 两种读法**都不按「状态 × 主题 × 屏宽」出图**：3 路径 × 3 态（未选 / 选中 / 封缄）× 2 主题（昼 / 夜）× 2 屏宽 = 36 张，且任何一次文案或数值改动都要重出。正解见 §1。

## 1. 核心判断：按「层」出图，不按「状态」出图

| 层 | 承担什么 | 谁来做 |
|---|---|---|
| L0 章节底 | 帷幕被掀开的整体氛围 | 生图 1 张（A） |
| L1 门体材质 | 三条路径各自的「这是什么文明」 | 生图 3 张（B/C/D） |
| L2 面板底纹 | 展开面板的材质延续 | **建议先用门体裁切 + CSS**，不够再补 3 张（G/H/I） |
| L3 状态 | 未选 / 选中 / 封缄 / 禁用 / 昼主题 / 390px | **全部 CSS**，demo 已验证三种封缄材质 |
| L4 文字与数值 | 路径名、得到 / 付出、帷幕点、周期累计、节点价格、第 K 重、i18n | **全部 DOM**，永不进图 |

三条硬理由：

1. **i18n 与动态数值**：TapTap 目前 zh-CN，但项目已有繁中待译 key、将来有英文；帷幕点余额、本周期累计、`C1–C5` 节点价格全是待标定的动态值。烧进图 = 每次标定重出图。
2. **Gemini 出中文几乎必然糊字**：项目已有「判断图上文字必须裁切放大 2~3×」的教训，曾把整图读错标题。图里出现汉字会直接制造不可验收的资产。
3. **状态是运行时产物**：封缄是 `veil.path` 选定后当场发生，选中态、昼主题 `html[data-ui-theme="day"]`、`prefers-reduced-motion` 都是玩家侧开关，不该固化成图。

> 外部方法论依据：`afovea/game-dev-skills → game-ui-ux-framework` 的 "never baked into textures" 与 clarity > immersion；`Mutakisa/game-slop-purge` 的「同一数值别重复显示、别堆泛光」。

**张数结论**：最小可交付 **4 张**（A + B/C/D）；把乙读法与面板底纹全做满 **9 张**。4 张 ≈ 1.05MB，9 张 ≈ 2.2MB，对现有 57MB 包增量 ≤4%。

## 2. 素材清单与命名（沿用现有 `assets/` 体系）

新目录 `assets/veil/`，命名对齐 `wonders/generated-v2/wonder-*.webp` 与 `tech-icons/era-N/*.png` 的短横线风格。

| 编号 | 文件 | 画幅 | 目标尺寸 | 单张预算 | 用途 | 必需 |
|---|---|---|---|---|---|---|
| A | `veil-curtain.webp` | 3:4 竖 | 1024×1365 | ≤300KB | 掀幕章节总底 / 重置预览背景 | 是 |
| B | `veil-door-si.webp` | 3:4 竖 | 768×1024 | ≤250KB | 硅基承续门体 | 是 |
| C | `veil-door-vo.webp` | 3:4 竖 | 768×1024 | ≤250KB | 虚境升华门体 | 是 |
| D | `veil-door-bl.webp` | 3:4 竖 | 768×1024 | ≤250KB | 渊血演化门体 | 是 |
| E / F | `veil-curtain-k2.webp` / `-k3.webp` | 3:4 竖 | 1024×1365 | ≤300KB ×2 | 第 2 / 3 重裂隙变体（乙读法） | 可选 |
| G / H / I | `veil-detail-si/vo/bl.webp` | 可平铺 | 768×768 | ≤200KB ×3 | 展开面板底纹 | 可选 |

**尺寸推导**（对齐 `render-content.js:248-251` 的既有依据）：

- 桌面三列卡片 ≈ `310 × 272` CSS px（980px 容器 / 3 − gap），2× DPR ⇒ `620 × 544`。
- 390px 单列 ≈ `343 × 212` CSS px，2× DPR ⇒ `686 × 424`。
- 取 **768 × 1024 竖版** + `background-size:cover` + `background-position:center top`，两种宽高比都能裁，与「880² = 2× 440px 浮层」同一套算法。
- Gemini 出图 ≥1536×2048，落盘前用 **Lanczos 降采样 → webp q=0.85 → RGB**（现有奇观图实测 274KB / 880²）。
- 引用路径写 `?v=1`；以后换图必须 bump（现有 `?v=2` / `?v=3` 手写惯例），`main.css` 的 `@import ?v=` 另算。

## 7. 性能账（数字带推导 / 讲机制 / 讲边界）

**预算推导**：60fps ⇒ 16.6ms/帧；背景与氛围预算取 1/8 ≈ **2ms/帧**。静态 `background-image` 只参与 Composite，单张合成约 0.02–0.05ms，4 张 ≈ 0.2ms，占预算 10%。真正贵的是**一次性解码**：768×1024 RGB ≈ 2.36MB 未压缩像素，webp 解码在中端手机约 8–20ms/张；4 张同帧解码 ⇒ 32–80ms，会直接吃掉 2–5 帧，表现为进面板时一次明显卡顿。

**机制**：图片走「下载 → 主线程解码 → GPU 纹理上传 → 合成」。解码与上传都不在合成线程，躲不掉；只有之后的静态展示便宜。反过来，1080p 全屏一次 `filter:blur()` / `backdrop-filter` 是 4–8ms，逐帧改一次就爆掉整帧预算；所以扫光必须 `transform:translateX`，淡入必须 `opacity`。

**内存边界**：解码后常驻 2.36MB/张 × 4 ≈ 9.4MB；叠加现有 `background.js` 双层 1600×900 序列帧 ≈ 5.8MB × 2 = 11.5MB ⇒ 峰值约 **21MB** 纹理内存，低端机需要盯。包体增量 4 张 ≈ 1.05MB / 9 张 ≈ 2.2MB，对 57MB 包 ≤4%。

**失效场景**：① 前 3 分钟不烫 ≠ 没问题，thermal throttle 常在 20 分钟后显形；② 120Hz 手机上 rAF 翻倍（今早星图 iframe 双 rAF 发热的教训）；③ 切走 tab 时 `.hidden{display:none}` 只停 rAF，**CSS animation 未必停**，需 `animation-play-state:paused` 或 `document.hidden` 守卫；④ 大面积半透明叠层吃手机 GPU 带宽，压底渐变要单层、不要叠三张图。

**检查清单**

- [ ] 首屏只解码可见的 3 张门体，A / 可选图懒加载，`decoding="async"`
- [ ] 单张 ≤300KB、webp q=0.85、RGB、Lanczos 降采样到 768×1024
- [ ] 动效只写 `transform` / `opacity`，循环动效 60fps 钳 + `document.hidden` 守卫
- [ ] 切 tab 停 CSS 动画；reduce-motion 全停且状态常驻
- [ ] 图加载失败时纯 CSS 兜底可用，功能不降级
- [ ] 三路径靠文字 + 形状 + 图标区分，不靠三套霓虹色
- [ ] 390px 无横拖；封缄态裁切放大后文字逐字可读
- [ ] 改过的 js/css 各自 `?v` bump，`main.css` 的 `@import` 别漏

**验收方法**：DevTools 录 20s 看 Main 线程（解码尖峰）与 Composite 层占用；真机挂 20 分钟摸温度；Network 面板确认首屏图片总字节 ≤1.1MB。
